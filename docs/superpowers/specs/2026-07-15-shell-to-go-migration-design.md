# Дизайн: выбор технологии взамен shell-логики

**Дата:** 2026-07-15
**Статус:** утверждён (brainstorming), готов к написанию плана
**Автор:** Claude (Opus 4.8) + Stsiapan
**Связано:** STS-74 (выбор технологии, эта задача), реализация вынесена в отдельную задачу
**Ревью:** Codex (gpt-5.5, high) прошёл, вердикт REVISE, находки учтены (см. «След ревью»)

## Проблема

Вся логика деплоя написана на bash: `setup.sh` плюс 10 модулей `lib/*.sh`, около 600 строк,
и около 800 строк тестов в `skills/tools/`. Bash даёт переносимость и отсутствие зависимостей,
но код тяжело читать и поддерживать, а проект пишется через ИИ и растёт.

Проблема не абстрактная. Конкретные её проявления в текущем коде:

1. **Stringly-typed булевы через позиционные аргументы.** `setup.sh:56` вызывает
   `deps_apply "$c7_dep" "$pw_dep" "$az_dep" "$ado_dep" "$dn_dep" "$cr_dep"`: шесть подряд
   идущих булевых строк. Перепутанный порядок не ловится ничем, ни компилятором, ни рантаймом.
   Та же схема в `settings_apply` и `skills_apply` (`profiles.sh:8-9,20-21`).
2. **Язык не тянет собственную предметную область.** Bash не умеет JSON, поэтому Python уже
   стал вторым языком: `lib/py/config_io.py` (64 строки), `lib/py/jsonmerge.py` (50),
   `claude/mcp/build_servers.py` (46), плюс inline `python3 -c` в `setup.sh:34,61,75`.
   Граница sh/py проходит через subprocess: каждое чтение ключа конфига (`config.sh:9-13`) это
   отдельный запуск интерпретатора.
3. **Интерпретатор на горячем пути.** `statusline.sh:5` на каждый рендер статусной строки
   поднимает `bash` + `cat` + `python3`, чтобы распарсить JSON со stdin. Это около 25-40 мс на
   рендер ради разбора одного маленького объекта.

## Цель

Один типизированный язык вместо связки bash + Python, без потери свойств текущей доставки:
машина не должна доустанавливать ничего сверх того, что уже ставит бутстрап, а контракт с
репозиторием `dotfiles` должен остаться неизменным.

## Ограничения (проверено на этом репозитории)

Первые три пункта определяют решение сильнее всего.

- **Доставку владеет chezmoi, а не этот репозиторий.** `chezmoi init --apply stpntkhnv/dotfiles`
  ставит `claude` CLI, тянет claudefiles как `git-repo` external в `~/.local/share/claudefiles`
  и через `run_after`-триггер запускает `setup.sh`, сравнивая HEAD чтобы не гонять зря
  (`README.md:53`, `README.md:118`). Проверено на машине: `~/.local/share/claudefiles` это
  полноценный клон со своим `.git`. Следствия:
  - Исходники **гарантированно** есть на машине всегда. Клон не опция, его делает chezmoi.
  - Точка входа это `setup.sh`. Её контракт задан в **другом** репозитории (`dotfiles`,
    `run_after_setup-claudefiles.sh.tmpl`), менять его дорого и вне объёма задачи.
  - HEAD-compare (`lib/apply-if-changed.sh`, стейт `last-applied-head`) означает, что setup
    отрабатывает только при смене HEAD external'а.
  - **`lib/apply-if-changed.sh` это публичный API этого репозитория, а не внутренний модуль.**
    Триггер в `dotfiles` его именно `source`-ит и зовёт функцию `apply_if_changed "$head" run`
    (см. план `2026-07-04-claudefiles-config-ownership.md:963,976,1016`: helper вынесен в
    claudefiles специально, «so the HEAD-compare logic is testable outside chezmoi»). Значит
    этот файл обязан остаться bash-функцией с тем же именем и сигнатурой. Он единственный
    `lib/*.sh`, который переживает миграцию.
- **`settings.json` держит абсолютные пути внутрь репозитория.** `settings.sh:7-9` подставляет
  в шаблон плейсхолдеры `<STATUSLINE_PATH>`, `<HOOK_PATH>`, `<SOUND_PATH>` реальными путями
  вида `$repo/claude/statusline/statusline.sh`. Плюс `skills.sh:31` делает
  `ln -sfnT "$root/claude/skills/dotnet-router"`. Репозиторий это постоянный рантайм-артефакт
  по построению, и это нормально: chezmoi его и держит.
- **Часть артефактов принципиально рантайм-овая.** `skills.sh:22-24` клонирует сторонний
  `dotnet/skills`, `skills.sh:27` генерирует каталог с абсолютными путями этой машины.
- **Мерж JSON принципиально бесхемный.** `invariants.md:9` требует, чтобы при миграции
  super в vanilla пользовательский контент и неизвестные ключи сохранялись. Значит инструмент
  обязан переписывать чужой `settings.json`, не зная его схемы.
- **`git` остаётся зависимостью в любом случае** (клон `dotnet/skills`, `skills.sh:24`).
- **Окружение машины на момент решения:** python 3.14.6, go присутствует, dotnet SDK 10.0.109,
  rust отсутствует.

## Не-цели (осознанный YAGNI)

- Кроссплатформенность за пределы Linux. Инструмент завязан на pacman (`deps.sh:6-18`).
- Изменение контракта с репозиторием `dotfiles` (external плюс `run_after` плюс HEAD-compare).
- Перенос `gen-dotnet-catalog.sh` (138 строк awk) и его теста. Отдельный генератор, отдельное
  решение, вне объёма.
- Переписывание `skills/dotnet-skills/**` (сторонний репозиторий) и `legacy/**`.
- Смена поведения. Миграция обязана быть поведенчески нейтральной.

## Решение

**Go, только стандартная библиотека. Бинарь собирается на месте из клона, который chezmoi уже
доставил. `setup.sh` остаётся точкой входа и превращается в тонкий шим.**

### Почему Go

1. **Только компилируемый язык чинит горячий путь.** `statusline.sh` поднимает интерпретатор
   на каждый рендер. Бинарь отвечает за ~2 мс вместо ~30 мс. Ни Python, ни bash этого не
   исправляют в принципе.
2. **Типы снимают текущий класс багов.** Шесть позиционных булевых строк (`setup.sh:56`)
   становятся структурой с именованными полями, ошибка ловится на компиляции.
3. **Ноль сторонних зависимостей.** `os/exec`, `encoding/json`, `flag` покрывают всю
   предметную область. Дух «нет зависимостей» сохраняется буквально, `go.sum` пустой.
4. **Бесхемный мерж ложится на язык естественно.** `map[string]any` из `encoding/json`
   мержит чужой JSON, сохраняя неизвестные ключи, без описания схемы.
5. **Прецедент в том же домене.** chezmoi, менеджер dotfiles, написан на Go.

### Почему сборка на месте, а не GitHub Releases

Изначально рассматривалась доставка бинаря через GitHub Releases и `curl`. Отклонено после
того, как выяснился факт про chezmoi-external. Причины по убыванию силы:

1. **Version skew, структурный дефект.** HEAD-compare срабатывает на смену HEAD external'а
   (`apply-if-changed.sh`), а релизный бинарь собран с тега. Любой коммит без релиза означает,
   что `setup.sh` скачает бинарь, не соответствующий исходникам, которые chezmoi только что
   доставил. Сборка на месте исключает рассинхрон по построению.
2. **Выгода уже получена бесплатно.** Единственный смысл Releases был в самодостаточном
   артефакте без клона. Но клон делает chezmoi, всегда. Скачивать бинарь в каталог, где уже
   лежат его исходники, не имеет смысла.
3. **Ломает тесты.** `test-setup-idempotent.sh:31` и `test-multiprofile.sh:21` запускают
   `bash "$cf/setup.sh"` в песочнице. `curl` за релизом потащил бы сеть в тест.
4. **Лишняя машинерия.** CI и релизы ради выгоды, которой нет.

Цена решения: `go` становится зависимостью машины вместо `python3`. Это идиоматично для
проекта: `deps.sh` уже предлагает доустановить `dotnet-sdk`, `nodejs`, `chromium`
(`deps.sh:70-80`). Сборка редкая: HEAD-compare пускает setup только при смене HEAD, а Go
собирает такой объём за секунды.

Установку `go` обязан делать сам `setup.sh` (шим), а не модуль `deps`: `deps` живёт внутри
бинаря, поэтому не может отвечать за наличие тулчейна, который этот бинарь собирает.

### Рассмотренные и отклонённые варианты

**Python.** Честно более дешёвый путь, и это фиксируется осознанно. Уже обязателен
(`setup.sh:7` делает `require_cmd python3`), уже 160 строк в репозитории, ноль шага сборки,
наименьшая церемония для subprocess-клея, миграция могла бы идти инкрементально по модулю.
Отклонён по одной причине, которая осталась после уточнения фактов: не чинит горячий путь
`statusline.sh`. Аргумент «не даёт самодостаточного артефакта» снят как неактуальный, клон и
так гарантирован. Цена решения: новый язык и шаг сборки, принята сознательно.

**Гибрид: компилируемый только горячий путь.** Портировать в маленький бинарь лишь
`statusline` и `detect-dotnet`, а логику деплоя свести в один Python-CLI, оставив shell как
оркестратор. Даёт выигрыш на горячем пути дешевле всего и снимает границу sh/py в логике.
Отклонён: оставляет три языка вместо одного (shell плюс Python плюс Go) и не решает проблему
пункта 1 (позиционные булевы строки живут в shell-оркестраторе). Это компромисс, который
консервирует ровно ту сложность, ради устранения которой затевается задача.

**C#.** Родной язык автора, что весомо для читаемости. Отклонён по стоимости тулчейна и
bootstrap, а не по возможностям языка:

- Циклическая зависимость: инструмент сам ставит `dotnet-sdk` по флагу (`deps.sh:76`), значит
  SDK не может быть его предусловием.
- Установленный SDK 10.0.109 это feature band 10.0.100, а `#:include`/`#:exclude` требуют
  10.0.300+. На текущем SDK вся логика file-based app жила бы в одном файле.
- Полноценный `.csproj` с AOT снимает предыдущий пункт, но требует SDK (~1GB) и линковочных
  зависимостей на машине ради результата, который Go даёт заметно меньшей ценой.
- Скилл `csharp-scripts` в разделе «When Not to Use» исключает file-based вариант дважды:
  «shell/Python/PowerShell-style automation» и «large enough that project structure, build
  customization, tests, or publish configuration should live in a `.csproj`».

Уточнено по ревью: утверждать, что AOT делает бесхемный JSON невозможным, **некорректно**.
`JsonNode`/`JsonDocument` это DOM-API, они работают без рефлексии и под AOT, а сам AOT
отключается через `#:property PublishAot=false` (см. таблицу свойств в `csharp-scripts`).
JSON здесь не аргумент ни за, ни против.

**Rust.** Сильные стороны не применимы: нет CPU-bound участков, нет конкурентности, нет FFI,
процесс живёт секунды и ждёт `pacman`. Применимы издержки: CLI на практике тянет
`serde`/`clap`/`anyhow` против stdlib-only у Go, компиляция десятки секунд против единиц,
borrow checker это недели для C#-разработчика ради 600 строк клея. Единственный кандидат,
которого нет на машине.

Уточнено по ревью: `serde_json::Value` **умеет** произвольный JSON, формулировка «serde
бесполезен» была бы неверной. Точная формулировка: главный козырь serde (типизированный
derive) на бесхемном мерже не окупается, поэтому преимущество Rust над Go здесь сжимается до
нуля, а издержки остаются.

## Целевая архитектура

Архитектура доставки **не меняется**: chezmoi тянет external, дёргает `setup.sh` по смене
HEAD, `settings.json` держит абсолютные пути в клон. Меняется только то, чем исполняется
логика. Это осознанно: чем меньше сдвиг, тем дешевле доказать поведенческую нейтральность.

```
cmd/claudefiles/          подкоманды: setup, statusline, detect-dotnet, verify
internal/
  config/                 заменяет config.sh + lib/py/config_io.py
  settings/               заменяет settings.sh + lib/py/jsonmerge.py
  mcp/                    заменяет mcp.sh + claude/mcp/build_servers.py
  skills/  plugins/  claudemd/  deps/  profiles/
setup.sh                  шим ~15 строк: обеспечить go, go build -o .bin/claudefiles, exec
lib/apply-if-changed.sh   остаётся bash: его source-ит триггер в dotfiles
skills/tools/gen-dotnet-catalog.sh  остаётся как есть, вне объёма
.bin/                     артефакт сборки, в .gitignore
```

Итог по файлам: из `lib/*.sh` выживает ровно один (`apply-if-changed.sh`), остальные девять
и все три `.py` уходят в `internal/`.

Один бинарь заменяет три вида кода: bootstrap (`setup.sh` плюс `lib/*.sh`), рантайм-хуки
(`statusline.sh`, `detect-dotnet.sh`) и Python-помощники.

`go:embed` **не нужен**: ассеты (`claude/settings/*.template.json`, `claude/skills/*/SKILL.md`,
`ready.wav`) доставляет chezmoi вместе с клоном, и пути на них уже абсолютные в клон.

Плейсхолдеры шаблонов (`settings.sh:10`) переживают миграцию: `<STATUSLINE_PATH>` начинает
рендериться в `$repo/.bin/claudefiles statusline` вместо пути к `.sh`. Механизм тот же.

Границы модулей сохраняются от текущих: appliers идемпотентны и владеют своим артефактом
(`architecture.md:126`). Изоляция профилей, сегодня реализованная субшеллом с экспортом env
(`profiles.sh:73`), становится явным параметром вместо глобального состояния.

## Миграция и тестирование

Тест-сьют разделён по судьбе. Проверено чтением каждого файла:

| Тесты | Судьба |
|---|---|
| `test-setup-idempotent.sh:31`, `test-multiprofile.sh:21` (зовут `bash setup.sh`), `test-secrets-not-tracked.sh` (чистый git-чек) | Переживают без правок: точка входа `setup.sh` сохранена |
| `test-statusline.sh:4`, `test-detect-dotnet.sh:6` (зовут скрипт по пути) | Правка пути на подкоманду бинаря, логика проверок остаётся |
| 7 юнит-тестов с `source lib/*.sh` (`test-config`, `test-settings`, `test-skills`, `test-plugins`, `test-profiles`, `test-mcp`, `test-claudemd`) плюс `test-deps.sh` (изолирует PATH под `lib/deps.sh`) | Портируются в Go table-тесты, песочница через `t.TempDir()` |
| `test-head-compare.sh` | Остаётся bash без правок: тестируемый им `apply-if-changed.sh` тоже остаётся bash (контракт с `dotfiles`) |
| `test-gen-dotnet-catalog.sh` | Не трогаем, генератор вне объёма |

Подмена внешних команд переживает миграцию: `faketools.bash` стабит `claude` через PATH, а
`exec.Command` в Go так же уважает PATH.

**Критерий катовера:** каждый инвариант из `invariants.md` закрыт приёмкой на Go-бинаре.
Отображение обязательно построить в плане реализации, поимённо, а не «в целом». Особого
внимания требуют те, что не проверяются чёрным ящиком напрямую:

- сохранение неизвестных ключей и снятие управляемых ключей при super в vanilla
  (`invariants.md:9`),
- `chmod 600` на `secrets.json` и MCP-манифестах (`invariants.md:6`),
- не-фатальность `deps` и `plugins`: сегодня это поведение под `set -e` (`invariants.md:13`),
  в Go оно становится явной обработкой ошибок и обязано быть проверено отдельно,
- whole-token матчинг (`invariants.md:11`),
- неклоббер чужого wrapper'а и идемпотентность симлинка (`invariants.md:10`).

Порядок: сначала чёрный ящик зеленеет на Go-бинаре, потом портируются юниты, потом удаляется
bash. Пока чёрный ящик красный, катовера нет.

## Риски

- **Регресс поведения при переписывании 600 строк.** Митигация: чёрный ящик как критерий
  катовера, поимённое отображение инвариантов, поведенческая нейтральность как требование.
- **Не-фатальность перестаёт быть свойством языка.** В bash её даёт `|| true` и `return 0`
  под `set -e`. В Go каждый такой путь придётся написать руками, и забытый `return err`
  уронит setup там, где сегодня был `warn`. Самый вероятный источник регресса.
- **`go` как новая зависимость машины.** Митигация: ставится шимом по образцу
  `deps.sh:70-80`; сборка редкая благодаря HEAD-compare.
- **Рантайм-артефакт перестаёт быть трекаемым файлом (новый класс отказа).** Сегодня
  `statusline.sh` лежит в git, поэтому external гарантирует его наличие. Завтра
  `settings.json` будет указывать на `.bin/claudefiles`, который является продуктом сборки и
  лежит в `.gitignore`. Если `.bin` удалить, а HEAD не менялся, то `run_after`-триггер в
  `dotfiles` **не позовёт** `setup.sh` (HEAD-compare, `apply-if-changed.sh`), и статуслайн
  останется сломанным до следующего коммита. План реализации обязан это закрыть: либо шим
  пересобирает по «бинарь отсутствует ИЛИ HEAD сменился», либо HEAD-compare учитывает наличие
  артефакта. Само по себе решение это не отменяет, но дырку надо закрыть осознанно.
- **Новый язык для автора.** Митигация: только stdlib, без фреймворков; 600 строк
  прямолинейного клея посильны для входа.

## Критерий готовности решения (эта задача)

Решение принято, обоснование зафиксировано, создана связанная задача на реализацию.
Реализация в объём STS-74 не входит.

## След ревью

Codex (gpt-5.5, high reasoning), вердикт REVISE. Принято:

- **P1 доставка против chezmoi.** Найден пропущенный факт (`README.md:53,118`). Следствие
  оказалось сильнее замечания: доставка через Releases отклонена как структурно дефектная
  (version skew), архитектурный сдвиг с `go:embed` и переездом data-каталога снят целиком.
- **P1 неточный сплит тестов.** Пересчитан по файлам, добавлены пропущенные `test-deps.sh`,
  `test-detect-dotnet.sh`, `test-gen-dotnet-catalog.sh`, введена честная категория «правка
  пути» вместо «переживает без изменений».
- **P2 фактические натяжки про .NET и Rust.** Исправлены: `JsonNode`/`JsonDocument` работают
  под AOT, `PublishAot=false` существует, `serde_json::Value` умеет произвольный JSON.
