# Linear MCP по флагу

Дата: 2026-07-28. Статус: дизайн утверждён, ждёт плана.

## Задача

Linear MCP приходится подключать руками на каждой машине и в каждом профиле. `setup.sh` уже умеет
раскатывать MCP-серверы по флагам (`claude/mcp/build_servers.py`, `lib/mcp.sh`), но Linear в этом
наборе нет. Нужен флаг, который ставит Linear во все выбранные профили и доводит его до рабочего
состояния, а не только до записи в конфиге.

Linear отличается от всех уже поддержанных серверов: это не stdio-процесс на `npx`, а удалённый
HTTP-сервер `https://mcp.linear.app/mcp` с OAuth 2.1 и динамической регистрацией клиента. Отсюда два
следствия. Первое: ему не нужны ни node/npx, ни секрет в `secrets.json` — конфиг сервера состоит из
типа и URL. Второе: одной записи в конфиг мало, нужен интерактивный вход в браузере
(`claude mcp login linear`), которого в claudefiles до сих пор не было ни для одного сервера.

## Решение: обычный флаг плюс отдельная фаза логина

Конфигурация сервера идёт по существующему пути (флаг → `build_servers.py` → `mcp_apply` →
манифест). Логин выносится в самостоятельную фазу `setup.sh` после провижна и не встраивается в
рецепты: браузерный OAuth посреди установки профиля не должен иметь возможности уронить профиль.

Профили: vanilla, super и g одинаково. Пользователь работает с задачами из любого профиля, и флаг
один на весь прогон — как `context7`.

## Флаг и вопрос

`flags.linear` в `secrets.json`, prompt-once по общей конвенции (`lib/config.sh:46-56`). Вопрос
задаётся в `config_ensure_all` сразу после блока context7 (`setup.sh:49-52`) — на верхнем уровне, а
не внутри ветки `profile_super`, потому что флаг кросс-профильный:

```
config_ensure_flag linear "Enable Linear MCP (issue tracker, OAuth login)? (y/N)"
```

Секретов флаг за собой не тянет: `config_ensure_optional` тут не нужен.

### Миграция на существующей машине

`config_ensure_flag` без TTY умирает с понятным сообщением (`lib/config.sh:54`). Значит на машине,
где `secrets.json` уже есть, но ключа `flags.linear` в нём нет, неинтерактивный прогон падает с
`missing required flag 'flags.linear'` — а chezmoi-триггер `run_after` ходит именно неинтерактивно.

Это не регрессия, а действующий контракт репозитория: ровно то же самое было при добавлении
`profile_gstack`, и в README есть готовый раздел про такую миграцию (`README.md:167`). Дефолтить
отсутствующий флаг в `false` без TTY дизайн не предлагает: это поменяло бы семантику для всех флагов
сразу и молча — вопрос за пределами этой задачи. Вместо этого README получает такую же заметку про
`flags.linear`: один интерактивный `./setup.sh` либо засев ключа вручную.

Тем же требованием накрыты фикстуры, прогоняющие `setup.sh` неинтерактивно (см. раздел «Тесты»).

## build_servers.py: ветка vanilla/g перестаёт быть early-exit

Сейчас vanilla и g уходят из скрипта на строке 28, напечатав только context7. Это и есть инвариант
«vanilla и g всегда ship context7 независимо от флагов» (`skills/tools/test-mcp.sh:13`,
`skills/tools/test-profiles.sh:107`). Инвариант остаётся, но ветка перестаёт быть терминальной:
context7 добавляется безусловно, Linear — по флагу.

```python
LINEAR = {"type": "http", "url": "https://mcp.linear.app/mcp"}

def context7_cfg():
    args = ["-y", "@upstash/context7-mcp"]
    if cfg.get("context7_api_key"):
        args += ["--api-key", cfg["context7_api_key"]]
    return {"type": "stdio", "command": "npx", "args": args}
```

vanilla/g: `servers["context7"] = context7_cfg()`, затем `if on("linear"): servers["linear"] = LINEAR`.
super: существующие ветки по флагам, `context7` через ту же `context7_cfg()`, в конце тот же
`if on("linear")`.

`context7_cfg()` убирает дубль сборки одного и того же конфига (сейчас `build_servers.py:24-27` и
`33-35`) — правка в том же файле и по тому же поводу, а не отдельный рефакторинг.

Порядок ключей в JSON влияет на манифест и на сравнение в `mcp_apply` только через равенство
словарей (`lib/mcp.sh:10-11`, сравниваются распарсенные объекты), поэтому позиция `linear` в выводе
значения не имеет.

## Снятие флага

Отдельного кода не требуется. `mcp_apply` удаляет ровно те серверы, что перечислены в прошлом
манифесте (`lib/mcp.sh:14-17`), поэтому `flags.linear: false` на следующем прогоне снимает сервер с
**выбранных** профилей.

Формулировка точная намеренно: `setup.sh` провижнит только профили из `selected` (`setup.sh:77-84`),
поэтому у профиля, который был установлен раньше, а теперь не выбран, останутся и его манифест, и
его сервер. Это общее свойство всех флагов, а не Linear: отключённый `profile_super` точно так же
оставляет `~/.claude-super` нетронутым. Уборку за невыбранными профилями дизайн не добавляет — на то
есть чистая установка.

OAuth-токен claudefiles не трогает ни при каком снятии флага — как не трогает `~/.codex/auth.json`.

## Логин: гейт на статусе, а не на факте добавления

`claude mcp get linear` печатает статус сервера. На неавторизованном:

```
linear:
  Scope: User config (available in all your projects)
  Status: ! Needs authentication
  Type: http
  URL: https://mcp.linear.app/mcp
```

(проверено на claude 2.1.220). Строка `Needs authentication` и есть гейт. Новая функция в
`lib/mcp.sh`:

```
mcp_linear_login()   # <profile> — никогда не фатальна, всегда return 0
  flags.linear != true                        -> return 0
  claude недоступен                           -> warn, return 0
  status="$(timeout 30 "$cb" mcp get linear 2>&1 || true)"
  status без "Needs authentication"           -> return 0   # вошли, или статус неизвестен
  есть TTY   -> timeout 300 claude mcp login linear ; при ненулевом коде warn с ручной командой
  нет TTY    -> warn "run: claude mcp login linear"
```

Три детали, без которых «никогда не фатальна» — пустое обещание. `setup.sh` идёт под
`set -euo pipefail`, поэтому статус захватывается с `|| true`: `mcp get` на отсутствующем или
недоступном сервере возвращает ненулевой код, и голое присваивание убило бы прогон. Оба вызова
обёрнуты в `timeout`: `mcp get` бьёт по сети, и недоступный `mcp.linear.app` не должен подвешивать
установку; у логина лимит больше, потому что внутри живой человек в браузере. `2>&1` нужен, чтобы
статус искался и в диагностике на stderr.

Проверка доступности `claude` идёт через `claude_bin` из `common.sh` (`lib/common.sh:6`), как и всё
остальное в `mcp.sh`, а не через `_claude_present` из `deps.sh`. Это не стилистика: `test-profiles.sh:7`
и `test-mcp.sh:5` подключают `mcp.sh` без `deps.sh`, и зависимость от чужого модуля сломала бы их.

TTY проверяется через `_has_tty` (`lib/config.sh:15-17`), а не через голое `[ -t 0 ]`. Известный
нюанс: `CLAUDEFILES_ASSUME_TTY=1` форсит «есть TTY», и для шага, открывающего браузер, это выглядит
опаснее, чем для `read`. Второй TTY-абстракции дизайн всё же не заводит: `ASSUME_TTY=1` в репозитории
встречается только в тестах, а там `claude` — фейк, который никакого браузера не откроет. Заводить
ради этого расходящуюся проверку значит получить два разных ответа на вопрос «интерактивны ли мы» и
чинить это потом.

Полярность выбрана положительной намеренно: логин запускается только когда CLI прямо сказал, что
авторизация нужна. Если формат вывода когда-нибудь изменится, поведение деградирует в «не логинить и
промолчать», а не в «открывать браузер на каждом прогоне». Цена деградации мала: неавторизованный
сервер и так виден в `/mcp` и в стартовом уведомлении Claude Code.

Проверка статуса стоит одного health-check к `mcp.linear.app` (около секунды) на профиль за прогон,
и только при включённом флаге. Инвариант идемпотентности она не нарушает: он о состоянии на диске
(`docs/invariants.md:5`), а `mcp get` ничего не пишет. Существующие ассерты о втором прогоне
проверяют `plugin install` и `mcp add-json` (`skills/tools/test-setup-idempotent.sh:62-63`) — их
`mcp get` не задевает.

## Где вызывается фаза логина

В `setup.sh` после блока `verify` и после проверки `PROVISION_FAILED` (`setup.sh:95-97`): если
профили упали, спрашивать про браузер незачем. Каждый профиль — своя подоболочка со своим
`CLAUDE_CONFIG_DIR`, как в `provision_selected` (`lib/profiles.sh:92`):

```
if [ "$(config_flag linear)" = true ]; then
  log "linear auth"
  for p in "${selected[@]}"; do
    ( export CLAUDE_CONFIG_DIR="$(profile_dir "$p")"; mcp_linear_login "$p" )
  done
fi
```

Про хранение токена дизайн не делает предположений. По документации Claude Code токен лежит в
credentials-файле каталога конфигурации; у super и g `.credentials.json` — симлинк на
`~/.claude/.credentials.json` (`lib/profiles.sh:54-62`), и тогда после входа в первом профиле
остальные увидят «авторизован» и промолчат. Если токен окажется per-profile, цикл честно спросит
логин для каждого. Оба варианта корректны, отличается только число браузерных входов.

## Что не меняется

- **deps.** Linear — удалённый HTTP-сервер, ни node/npx, ни chromium ему не нужны. Сигнатура
  `deps_apply` и таблица зависимостей не трогаются.
- **clean.** Чистая установка стирает `secrets.json` и user-scope MCP-серверы, но сохраняет
  `.credentials.json` и `.claude.json` кроме `mcpServers` (`docs/invariants.md:18`). После clean флаг
  спрашивается заново, сервер добавляется заново, а фаза логина сама решит, нужен ли вход.
  `clean_verify` сверяет ключи манифеста с живым `.claude.json` — `linear` будет в обоих.
- **mcp_apply.** Работает с любым конфигом сервера как есть; для HTTP `add-json` принимает
  `{"type":"http","url":...}` без изменений (проверено вживую).
- **Имя `linear` в user scope.** Если пользователь ранее добавил сервер с этим именем руками,
  `mcp_apply` его перезапишет — это общее свойство всех управляемых имён, не новое.

## Тесты

`skills/tools/lib/faketools.bash` — фейковый `claude` учится двум подкомандам:

- `mcp get <name>` — печатает статус; needs-auth или ok переключается переменной окружения
  (`CLAUDE_FAKE_MCP_AUTH`), по умолчанию needs-auth для сервера, который есть в состоянии фейка.
- `mcp login <name>` — логирует вызов и **дописывает в ту же строку `CLAUDE_CONFIG_DIR`**.

Второе не косметика. Состояние фейка одно на весь фикстур-HOME
(`skills/tools/lib/faketools.bash:20-21`), поэтому без записи каталога тест не отличит «логин прошёл
по каждому выбранному профилю» от «логин прошёл трижды по дефолтному каталогу» — а именно это и есть
то, что фаза логина обязана делать правильно. Дописывание безопасно для действующих ассертов: они
все ищут подстроку (`grep -q "mcp add-json --scope user context7"`), а суффикс подстроку не рвёт.
Каталог дописывается только в ветке `mcp login`, чтобы не трогать формат остальных строк.

`skills/tools/test-mcp.sh` — новые проверки:

- vanilla с `flags.linear: true` -> ключи ровно `["context7", "linear"]`;
- vanilla без флага -> ровно `["context7"]` (действующий инвариант не сломан);
- super с флагом -> `linear` присутствует; форма записи ровно `{"type":"http","url":"https://mcp.linear.app/mcp"}`,
  никаких `env` и заголовков;
- `mcp_linear_login` в четырёх состояниях: флаг выключен -> ни одного вызова CLI; needs-auth плюс
  TTY -> в логе есть `mcp login linear`; статус ok -> `mcp login` не вызывался; needs-auth без TTY ->
  `mcp login` не вызывался, прогон не упал.

Фикстуры, которые прогоняют `setup.sh` неинтерактивно, получают `"linear": false`:
`test-setup-idempotent.sh:42` и `test-multiprofile.sh:17,65` (обе зовут `bash setup.sh
--non-interactive`). Там же в `test-setup-idempotent.sh:108` добавляется ответ на новый вопрос в
строке ответов интерактивного clean-прогона — вместе с её комментарием, перечисляющим ответы по
порядку. Промолчать нельзя: хвостовые пустые строки поглотили бы вопрос и молча записали `false`.

`test-profiles.sh` править не нужно: он подключает модули и зовёт рецепты напрямую, минуя
`config_ensure_all`, а его ассерт `list(d) == ["context7"]` для профиля g (строка 107) остаётся
верным при отсутствующем флаге.

### Сквозной тест фазы логина

Юнит-проверок `mcp_linear_login` мало: самое рискованное место дизайна — проводка в `setup.sh`, а
она не проверяется ни одним из тестов выше. Поэтому отдельный сценарий через настоящий `setup.sh`
(`test-multiprofile.sh` — там уже подняты несколько профилей и фейковый `claude`), с
`flags.linear: true` и `CLAUDEFILES_ASSUME_TTY=1`:

- `mcp login linear` встречается ровно по разу на каждый выбранный профиль, и `CLAUDE_CONFIG_DIR` в
  строке лога — каталог именно этого профиля;
- при статусе ok (`CLAUDE_FAKE_MCP_AUTH=ok`) ни одного `mcp login` — защита от «браузер на каждом
  прогоне»;
- при упавшем профиле фаза не выполняется вовсе: `setup.sh` уходит в `exit 1` раньше
  (`setup.sh:95-97`). Провал форсится тем же приёмом, что в `test-profiles.sh:57-62` — `claude`,
  который не отражает установленный плагин, роняет `recipe_super` на self-verify.

## Границы

- Аутентификация по личному API-ключу Linear через заголовок `Authorization` не поддерживается.
  OAuth — рекомендованный путь Linear, и он не требует хранить долгоживущий секрет ни в
  `secrets.json`, ни в MCP-манифесте.
- Полностью неинтерактивной установки Linear нет: браузерный вход остаётся ручным шагом, один раз на
  машину. Без TTY `setup.sh` печатает точную команду и продолжает.
- Выбор организации/команды Linear, фильтры и любые настройки внутри самого сервера вне области:
  claudefiles ставит сервер, а не конфигурирует Linear.
