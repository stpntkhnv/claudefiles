**Обновление 12 октября 2026:** память по Git remote теперь выбирается автоматически для любого Git-репозитория без регистрации. `setup.sh` устанавливает запускатель и его PATH самостоятельно. Индекс рабочей области передаётся отдельно от проектной памяти. [Текущее устройство, команды и границы](../repository-memory.md). Описание и канвас ниже сохраняют снимок настройки от 11 октября, до этого изменения; зелёный раздел на старом канвасе обозначен как предложение.

У тебя одна база знаний на диске: `/home/stsiapan/Documents/Notes/kb`. В контейнерах используются отдельные настройки Claude, но они указывают на эту же базу. При запуске Claude получает подходящие инструкции и короткие оглавления заметок. Подробные заметки он открывает отдельным чтением.

Здесь разобрана существующая настройка Claude Code на 11 октября 2026. Примеры путей взяты с этой машины. [Единый канвас TLDraw](agent-context.tldraw) содержит одну страницу со сквозным примером `digi3 → claude-super → ~/main/1ANV`: деревья папок, отдельные файлы, короткие примеры и явные симлинки. Его можно посмотреть также как [SVG](agent-context.svg) или [JPG](agent-context.jpg). Существующее подключение и предложенная память без привязки к пути клона на канвасе разделены. [Правила оформления](diagram-rules.md) встроены в скилл `tldraw-offline` и сохраняются для следующих ревью.

## Что означают папки на скриншоте

**База знаний**, **KB** и **волт** здесь означают одну папку с Markdown-файлами. Markdown — обычный текст с заголовками и ссылками; его можно открыть текстовым редактором. Obsidian и другие приложения показывают эти же файлы более удобно.

| Пункт в корне KB | Что хранится | Конкретный пример | Как попадает в сессию |
|---|---|---|---|
| `_source/` | Старые исходные копии памяти, использованные при сборке базы. Внутри есть `host`, `d3`, `d3s`, `pe`, `pes`, `st`, `sts`. | `_source/host/ado-mcp/MEMORY.md` — старый файл памяти из прежней раскладки. | Подключения этой папки через правила не найдено. Её можно открыть явно, например для восстановления старой записи. |
| `contexts/` | Заметки по рабочим областям `personal`, `digi3`, `stellium`. Внутри каждой области также есть заметки её проектов. | `contexts/personal/INDEX.md` перечисляет личные конвенции и подкаталоги проектов. | Оглавление выбранной области подключено через правило в `main` соответствующего контейнера. Вложенные оглавления и заметки читаются отдельно. |
| `global/` | Заметки, полезные в разных проектах и рабочих областях. | `global/feedback-annotate-jargon.md` — просьба объяснять технические термины простыми словами. | `global/INDEX.md` подключён через правила каждого профиля. Текст отдельной заметки читается по необходимости. |
| `machine/` | Факты о конкретном компьютере. Есть `laptop` и `tsikhanau-pc`. | `machine/tsikhanau-pc/INDEX.md` перечисляет заметки про Arch, niri, звук и клавиатуру этого компьютера. | На хосте подключён под `/home/stsiapan/system`. При запуске под `/home/stsiapan/main` это правило не находится в родительской цепочке. |

Остальные файлы читает отдельно. |
| `README.md` | Описание устройства базы для читателя: разделы, договорённости, история. | Файл, который ты видишь в корне KB. | Само имя `README.md` не подключает файл в сессию. Агент должен его открыть. |

В README базы написано, что старые исходники вынесены в `kb-archive/_source/`, но на этой машине папка `kb/_source/` тоже существует и содержит старые файлы. Описание и фактическая раскладка здесь расходятся. Наличие этой папки само по себе не включает её в стартовую загрузку.

### Почему папка projects встречается в двух местах

Эти два пути относятся к одному проекту, но служат разным целям:

```text
kb/contexts/personal/projects/claudefiles/
    INDEX.md
    заметки по понятному имени проекта

kb/projects/-home-stsiapan-main-claudefiles/memory/
    MEMORY.md
    рабочие заметки auto memory для этого пути репозитория
```

Первый путь — собранная по темам библиотека заметок. В документации KB она называется «канон»: место, где договорились держать основные заметки проекта. Название `claudefiles` не зависит от расположения его Git-клона.

Второй путь — папка, которую умеет выбирать сам Claude Code. Длинное имя — преобразованный путь `/home/stsiapan/main/claudefiles`. Этот преобразованный идентификатор иногда называют **slug**. Клон того же проекта в другой папке может получить другой идентификатор и отдельную память.

В существующем `MEMORY.md` для claudefiles записана ссылка на первый путь и просьба прочитать его, когда нужен контекст проекта. Так два места связаны. Общего автоматического переноса всех заметок из `projects/` в `contexts/` установщик не делает.

## Как работают вложенные области digi3

Сейчас в главном `kb/contexts/digi3/INDEX.md` есть четыре записи об общих заметках области, а затем раздел «Под-области» с тремя ссылками:

```text
projects/1anab/INDEX.md
projects/1anv/INDEX.md
projects/shared/INDEX.md
```

Это навигация по библиотеке. Например, агент получает главный индекс через контекстное правило, видит ссылку на `projects/1anv/INDEX.md` и может открыть её инструментом чтения. В открытом индексе он получает список заметок по 1ANV, выбирает нужную и читает её файл. Название `projects` здесь означает только способ разложить заметки по темам.

```text
При старте:
  запускатель передаёт индекс kb.context как справочные данные
    → kb/contexts/digi3/INDEX.md

После отдельного чтения:
  kb/contexts/digi3/projects/1anv/INDEX.md
    → нужная заметка из этой папки
```

В текущем установщике нет механизма, который сопоставляет открытый Git-репозиторий с одной из этих трёх папок и автоматически выбирает её индекс. Поэтому фраза «читаются по требованию» означает, что агенту нужно самостоятельно выбрать ссылку по задаче либо получить прямое указание её открыть. Это не гарантированная автоматическая загрузка памяти 1ANV.

`shared` тоже является разделом библиотеки: само название не связывает его с конкретным репозиторием и не задаёт область загрузки. Такой раздел может содержать знания для нескольких репозиториев; соответствие нужно задавать отдельно.

Таблицы «заметка / откуда взята» описывали происхождение записей при переносе. Они не участвовали в подключении контекста. По просьбе владельца эти таблицы удалены из главного индекса digi3 и трёх перечисленных вложенных индексов; списки заметок и ссылки сохранены.

## Как можно хранить память без привязки к пути клона

Хранить рабочую память непосредственно в `contexts/digi3/projects/1anv/` технически можно. Две отдельные системы хранения не являются обязательным условием Claude Code. В существующей настройке отдельно работают стандартный выбор памяти по пути репозитория и библиотека заметок с понятными именами; связывающего их автоматического выбора пока нет.

Если переименовать локальную папку, старая память физически останется в KB. Проблема в том, что стандартный выбор может открыть другую папку памяти, и новый разговор не получит прежний `MEMORY.md` автоматически.

Claude Code позволяет задать конкретную папку через `autoMemoryDirectory`. В отличие от используемого здесь `CLAUDE_CODE_REMOTE_MEMORY_DIR`, это путь **непосредственно к папке памяти выбранного проекта**, без автоматического добавления `projects/<путь>/memory`. [Документация выбора папки памяти](https://code.claude.com/docs/en/memory#storage-location).

Например, такая настройка направила бы чтение и запись auto memory в уже понятную человеку область:

```json
{
  "autoMemoryDirectory": "/home/stsiapan/Documents/Notes/kb/contexts/digi3/projects/1anv"
}
```

Это пример предлагаемой настройки, сейчас он не применён. Клиент ожидал бы `MEMORY.md` внутри этой папки. Существующий `INDEX.md` можно заменить единым оглавлением `MEMORY.md`, обновив ссылки, либо оставить имя `INDEX.md` как ссылку на тот же файл. Два независимо обновляемых оглавления не нужны.

### Как узнавать проект независимо от локального каталога

Само перемещение файлов не решает выбор папки памяти. Чтобы новый клон в `sources/whatever` узнал память прежнего клона в `main/1ANV`, нужен устойчивый идентификатор проекта.

Для твоего сценария подходит явное соответствие **адрес Git-репозитория → область и имя проекта в KB**. Git remote — сохранённый в клоне адрес удалённого репозитория. Он обычно одинаков у двух клонов, даже когда их локальные каталоги называются по-разному. Следует учитывать полный адрес организации и репозитория, а не только последнее имя `1ANV`; формы SSH и HTTPS можно привести к одному виду. При смене адреса или работе с форком нужна дополнительная привязка.

Предлагаемая цепочка выглядит так:

```text
любой локальный каталог клона
    → адрес Git-репозитория
    → явная привязка digi3/1anv
    → autoMemoryDirectory = KB/contexts/digi3/projects/1anv
    → MEMORY.md и заметки в одном месте
```

Такое соответствие можно хранить в настройках claudefiles и применять при запуске всех профилей. Для передачи вычисленного значения клиент поддерживает `--settings` с JSON; можно использовать и проектные настройки. [Документация CLI](https://code.claude.com/docs/en/cli-reference#cli-flags).

У общей профильной настройки одно значение для всех запускаемых проектов, поэтому нельзя просто вписать `.../1anv` в каждый профиль: тогда разные репозитории станут писать в память 1ANV. Выбор должен происходить для конкретного запуска. Локальная настройка только одного клона также не решает автоматическое подключение новых клонов; для этого нужен общий реестр привязок либо настройка, которая приходит вместе с репозиторием.

Одна логическая область KB при необходимости может соответствовать нескольким репозиториям. Неизвестный репозиторий следует явно привязать, а не угадывать по названию папки. Сам адрес Git не гарантирует, что конкретный репозиторий уже зарегистрирован в KB.

Перед переходом нужно объединить существующие записи: сейчас в индексе библиотеки 1ANV 25 заметок, а в его отдельной папке auto memory 21 Markdown-файл, включая `MEMORY.md`. Эти наборы нельзя просто считать одинаковыми и удалить один из них. После объединения новые сессии должны читать и писать в одно место.

Индекс рабочей области сейчас подаёт сам запускатель как справочные данные по настройке `kb.context`, независимо от имени зонтичной папки (`main`, `sources` или любой другой). Перенос памяти проекта не требует отдельной перенастройки индекса области: его на каждом старте подставляет запускатель, а не правило конкретной папки.

## Что такое INDEX.md

**Индекс — оглавление заметок в обычном текстовом файле.** Слово «индекс» здесь не означает поисковый сервер, векторную базу или специальный формат.

У тебя много файлов с одинаковым именем `INDEX.md`. Каждый описывает свою папку:

```text
kb/global/INDEX.md
    оглавление общих заметок

kb/contexts/personal/INDEX.md
    оглавление рабочей области personal

kb/contexts/personal/projects/claudefiles/INDEX.md
    оглавление собранных заметок проекта claudefiles

kb/machine/tsikhanau-pc/INDEX.md
    оглавление заметок этого компьютера
```

Например, в настоящем `global/INDEX.md` есть строка:

```text
- [[feedback-annotate-jargon]]: When using technical terms or rare words, add a short plain-language gloss in parentheses
```

`[[feedback-annotate-jargon]]` — ссылка в формате Obsidian на заметку `feedback-annotate-jargon.md`. Одна строка уже даёт агенту краткое представление о содержании. Чтобы получить полный текст, агент открывает:

```text
/home/stsiapan/Documents/Notes/kb/global/feedback-annotate-jargon.md
```

Само упоминание `[[...]]` не выполняет чтение этого файла. Обычная Markdown-ссылка `[текст](путь)` тоже не выполняет чтение. Поэтому «загрузился индекс» означает «в контексте появилось оглавление и краткие описания», а не «прочитана вся папка со всеми вложенными заметками».

`MEMORY.md` выполняет похожую роль оглавления, но его имя специально распознаёт механизм auto memory. Файлы `INDEX.md` в KB подключает наша настройка через `rules/`, либо агент читает их инструментом. Один только файл с именем `INDEX.md` где-нибудь на диске ничего автоматически не подключает.

Для индексов KB установщик задаёт договорённость держать примерно до 50 строк. Это просьба в инструкции агенту. Для начала `MEMORY.md` у Claude Code есть отдельный лимит загрузки: 200 строк или 25 КБ. Детальные заметки загружаются по запросу. [Документация auto memory](https://code.claude.com/docs/en/memory#how-it-works).

## Где именно лежат правила

Да, у профиля есть собственная папка `rules`. Кроме неё есть правила в рабочих папках.

**Профиль** — выбранный набор настроек одного Claude Code. **Рабочая область** — `personal`, `digi3` или `stellium`. Можно работать профилем `super` внутри любой из этих областей: это два независимых выбора.

Внутри контейнера `personal` домашняя папка `~` означает `/home/stsiapan/homes/personal`. Поэтому три профиля этого контейнера находятся здесь:

| Команда | Каталог профиля |
|---|---|
| `claude` при обычном запуске без переопределения конфигурации | `/home/stsiapan/homes/personal/.claude` |
| `claude-super` | `/home/stsiapan/homes/personal/.claude-super` |
| `claude-g` | `/home/stsiapan/homes/personal/.claude-g` |

Например, для `super` существуют:

```text
/home/stsiapan/homes/personal/.claude-super/
    CLAUDE.md          инструкции этого профиля
    settings.json      настройки клиента
    rules/
        kb.md          как читать и пополнять базу знаний
        kb-index.md    симлинк на общий global/INDEX.md
    skills/            инструкции для отдельных задач
    plugins/           установленные расширения
```

`CLAUDE.md` и файлы в `rules/` дают агенту текст. `settings.json` читает программа Claude Code: он задаёт переменные окружения, разрешения, хуки и включённые плагины. Сам JSON целиком не подставляется как твой промпт.

Правила рабочих папок лежат отдельно:

| Файл | Область действия в существующей настройке |
|---|---|
| `/home/stsiapan/homes/personal/.claude-super/rules/kb.md` | Запуски выбранного профиля `super` в этом контейнере. |
| `/home/stsiapan/homes/personal/.claude-super/rules/kb-index.md` | Общий индекс KB для этого профиля. Аналогичные ссылки есть в vanilla и g. |
| `/home/stsiapan/homes/personal/main/.claude/rules/context-index.md` (прежний симлинк — `setup.sh` его снимает) | Индекс рабочей области теперь передаёт запускатель как справочные данные на каждом старте, независимо от выбранного профиля и от имени зонтичной папки. |
| `<репозиторий>/.claude/rules/testing.md` | Инструкции проекта; это возможное место для нового правила, а не утверждение, что такой файл уже есть в каждом репозитории. |
| `/home/stsiapan/system/.claude/rules/machine-index.md` (прежний симлинк — вне контейнера тоже снимается `setup.sh`) | Индекс машины передаёт запускатель как справочные данные во всех сессиях этого хоста; внутри контейнера машинный слой не используется. |

Название `.claude` у **проектной** папки правил остаётся `.claude` и при работе через `claude-super`. Искать `main/.claude-super/rules` для подключения рабочей области не нужно. `.claude-super` — имя твоего пользовательского профиля, а `.claude/rules` внутри проекта или его родителя — соглашение самого Claude Code.

В обычной настройке файлы инструкций складываются: профиль плюс подходящие родительские папки плюс проект. Правила с ограничением `paths` подгружаются для подходящих файлов; правила без него доступны при старте в своей области. Симлинки в проектных правилах, ведущие наружу, могут требовать разового разрешения внешних импортов в текущей версии клиента. [Документация правил](https://code.claude.com/docs/en/memory#organize-rules-with-clauderules).

## Как симлинк подключает файл из базы

**Симлинк** — запись в файловой системе, которая перенаправляет открытие одного пути на другой. Например, существует:

```text
/home/stsiapan/homes/personal/.claude-super/rules/kb-index.md
    → /home/stsiapan/Documents/Notes/kb/global/INDEX.md
```

Когда Claude Code открывает `rules/kb-index.md`, операционная система возвращает текст целевого `global/INDEX.md`. Копия заметок в профиль не создаётся. Правка исходного индекса меняет то, что будет прочитано через ссылку при следующей загрузке.

Имя `kb-index.md` выбрал этот установщик, чтобы отличать эту ссылку от других файлов `rules/`. Для загрузчика Claude важно, что это подходящий `.md`-файл в `rules/`; программной команды «загрузи KB по имени kb-index» здесь нет. Прежние `context-index.md` и `machine-index.md` были такими же символическими ссылками, но теперь их снимает `setup.sh`: индексы области и машины подаёт запускатель как справочные данные на каждом старте, а не отдельный файл в `rules/`.

`rules/kb.md` отличается: это настоящий файл с инструкциями, который генерирует claudefiles. Он сообщает путь базы, описывает запись общих заметок и добавление строки в индекс. Он также велит считать подключённые индексы данными: описаниями заметок, которые не должны переопределять пользовательские инструкции.

## Кто выбирает рабочую область контейнера

Разделим настройку компьютера и каждый запуск Claude. Это разные моменты.

### При настройке через setup.sh

В контейнере `personal` файл

```text
/home/stsiapan/homes/personal/.config/claudefiles/secrets.json
```

содержит такую часть конфигурации:

```json
{
  "kb": {
    "vault_path": "/home/stsiapan/Documents/Notes/kb",
    "context": "personal"
  }
}
```

`vault_path` означает «где находится общая база», а `context` — «какую рабочую область подключить под `main` этого домашнего каталога». Имя файла `secrets.json` историческое; показанные два поля описывают пути и выбор области.

Установщик читает этот конфиг и делает две отдельные вещи:

1. Для каждого устанавливаемого профиля создаёт `rules/kb.md`, ссылку `rules/kb-index.md` на общий индекс и настройку хранилища auto memory.
2. Один раз для рабочей папки снимает прежние симлинки `context-index.md`/`machine-index.md`, если они ведут в этот волт: индекс области больше не заводится заранее, его на каждом старте подаёт сам запускатель.

Код первой части находится в [`kb_apply`](../../lib/kb.sh), второй — в [`kb_workspace_unwire`](../../lib/kb.sh) в том же файле. Настройку памяти и разрешений записывает [`kb_settings.py`](../../lib/py/kb_settings.py). Сам индекс области на старте передаёт [`kb_homes.py`](../../lib/py/kb_homes.py) через `repo_memory.py`.

Claude не обязан заново читать `secrets.json` при каждом старте: нужные настройки и ссылки уже созданы установщиком. Если изменить `kb.context`, для перенастройки ссылки нужен следующий запуск `setup.sh`.

### При запуске Claude

Представим конкретную работу внутри контейнера `personal`:

```bash
cd /home/stsiapan/homes/personal/main/Tripown
claude-super
```

Происходит следующая цепочка:

1. Обёртка `claude-super` задаёт `CLAUDE_CONFIG_DIR=/home/stsiapan/homes/personal/.claude-super` и запускает Claude Code. `CLAUDE_CONFIG_DIR` — переменная окружения, указывающая каталог профиля.
2. Клиент получает инструкции `CLAUDE.md` и правила выбранного профиля. Через `rules/kb-index.md` получает текст общего `global/INDEX.md`.
3. Клиент ищет инструкции по цепочке родительских папок рабочей директории. Для `.../personal/main/Tripown` родителем является `.../personal/main`.
4. Это не связано с родительскими правилами: ещё на шаге 1, определяя `kb.context`, запускатель передаёт `contexts/personal/INDEX.md` как справочные данные через дополнение системного промпта.
5. Если в самом `Tripown` есть подходящие инструкции, добавляются и они. Пустые или отсутствующие файлы ничего не добавляют.
6. Механизм auto memory выбирает память этого репозитория и загружает начало `MEMORY.md` по пути:

   ```text
   /home/stsiapan/Documents/Notes/kb/projects/
       -home-stsiapan-homes-personal-main-Tripown/memory/MEMORY.md
   ```

7. В `super` также работают стартовые хуки. Например, `detect-dotnet.sh` добавляет подсказку о `dotnet-router`, если находит признаки .NET-проекта. Это ещё один способ добавить текст в сессию.

Индекс области не зависит от глубины репозитория под `main`: запускатель подставляет одно и то же значение `kb.context` для всего окружения, независимо от того, насколько глубоко лежит репозиторий. Память самого репозитория всё равно выбирается по его пути — для неё нужно запускать сессию именно в нём, а не просто в домашней папке контейнера.

### Почему в другом контейнере получается другой контекст

На этой машине проверены следующие ссылки:

| Где запускаешь Claude | Какой `kb.context` подаёт запускатель | Куда ведёт индекс |
|---|---|---|
| `/home/stsiapan/homes/personal/main/Tripown` | `personal` | `kb/contexts/personal/INDEX.md` |
| `/home/stsiapan/homes/digi3/main/1ANAB` | `digi3` | `kb/contexts/digi3/INDEX.md` |
| `/home/stsiapan/homes/stellium/main/chatjti` | `stellium` | `kb/contexts/stellium/INDEX.md` |

У каждого контейнера свой домашний каталог, свой конфиг установщика и свои профили. У всех этих профилей общий индекс ведёт в один `kb/global/INDEX.md`, а `kb.context` каждого окружения задаёт свой раздел `contexts/`.

Имя контейнера само по себе не является командой загрузчику Claude. Работает значение `kb.context` этого окружения, которое запускатель передаёт как справочные данные на каждом старте. В конфигурации договорились использовать одинаковые имена контейнера и области KB, поэтому это выглядит как автоматический выбор по контейнеру.

Эта схема выбирает, какой индекс подставляется при старте. Она не является ограничением доступа ко всем остальным заметкам базы.

## Как подключена auto memory

В `settings.json` каждого из трёх профилей хоста и каждого проверенного контейнера есть настройка:

```json
{
  "env": {
    "CLAUDE_CODE_REMOTE_MEMORY_DIR": "/home/stsiapan/Documents/Notes/kb"
  }
}
```

В существующей реализации это **корень хранилища**. Claude Code добавляет `projects/<идентификатор пути>/memory/` для выбранного репозитория. Поэтому профили vanilla, super и g при работе в одном и том же репозитории используют одно место памяти.

Несмотря на слово `REMOTE`, в этой настройке указан обычный локальный путь. Здесь не настраивается запрос к облачному серверу памяти. Перенос файлов между устройствами делает Syncthing, настроенный отдельно в dotfiles.

У Claude Code также существует публичная настройка `autoMemoryDirectory`, но этот установщик сейчас записывает именно переменную выше. В проверенных настройках профилей `autoMemoryDirectory` не задан. При изменении способа подключения нельзя просто подставить корень всей KB как папку памяти одного проекта: нужно учитывать, какой путь ожидает выбранный механизм.

## Что уже получает агент и что ещё должен прочитать

Для примера `personal → Tripown → claude-super`, при обычной загрузке и разрешённых внешних ссылках:

| Уже добавляется к текущему разговору | Появится после дополнительного чтения или вызова |
|---|---|
| Базовые инструкции клиента и твоё сообщение | Полные заметки из `global/`, перечисленные в индексе |
| Подходящие `CLAUDE.md` и правила профиля `super` | Полные заметки рабочей области `personal` |
| Содержимое `global/INDEX.md` | Вложенные `contexts/personal/projects/<проект>/INDEX.md` и их заметки |
| Содержимое `contexts/personal/INDEX.md` | README базы знаний, исходники, спецификации и планы |
| Начало `MEMORY.md` памяти репозитория | Остальные файлы памяти репозитория |
| Текст стартовых хуков, если они его возвращают | Полный текст выбранного скилла и результаты MCP-инструментов |

Если индекс уже содержит короткое описание факта, агент видит это описание. Дополнительное чтение нужно для деталей. Важно различать «агент знает, что заметка существует», «агент получил краткое описание» и «агент прочитал заметку целиком».

## Что меняется при разных запусках

**Меняешь `claude-super` на `claude-g` в том же репозитории.** Меняются профильные инструкции, набор скиллов, плагины и хуки. Общий индекс, индекс родительской рабочей области и место auto memory остаются теми же при существующей настройке всех профилей.

**Меняешь `personal` на `stellium` и запускаешь сессию в его репозитории под `main`.** Меняется родительская ссылка на рабочую область. Общая KB остаётся той же. Память конкретного репозитория выбирается по его пути.

**Запускаешь Claude в `/home/stsiapan/homes/personal`, выше `main`.** Правило из `main/.claude/rules` не становится родительским: оно ниже рабочей директории. Нельзя считать индекс `personal` подключённым при старте только по факту входа в контейнер.

**Запускаешь Claude на хосте в `/home/stsiapan/main/claudefiles`.** На хосте `kb.context=none`; ссылки `main/.claude/rules/context-index.md` нет. Через профиль подключён общий индекс, через auto memory — `MEMORY.md` claudefiles. Внутри этого `MEMORY.md` есть ссылка на собранные заметки `contexts/personal/projects/claudefiles/INDEX.md`: агент может прочитать их по этой ссылке. Весь контекст `personal` автоматически таким способом не подставляется.

**Запускаешь Claude на хосте под `/home/stsiapan/system`.** В родительской цепочке появляется машинное правило, ведущее в `machine/tsikhanau-pc/INDEX.md`. Сам факт работы на этом компьютере не делает машинный индекс обязательной частью каждой сессии во всех папках.

**Меняешь заметку на другом устройстве.** Syncthing переносит файл базы. При следующей загрузке индекса или чтении заметки агент получает новый текст. Уже открытый разговор не получает весь изменившийся волт просто от события синхронизации.

## Остальные механизмы передачи контекста

| Механизм | Как именно добавляет текст | Пример в этой настройке |
|---|---|---|
| Сообщение и вложение | Ты передаёшь задачу или данные в текущий разговор. | Скриншот папок KB из этого диалога. |
| `CLAUDE.md` | Постоянные инструкции подходящей области. | В vanilla: `Write short and direct. No emojis.` В super: указание учитывать документы `docs/vision/`. |
| `rules/*.md` | Отдельные файлы инструкций или подключённых оглавлений. | `kb.md`, `kb-index.md`, `context-index.md`. |
| Импорт `@file` в `CLAUDE.md` | Подключает текст указанного файла при загрузке инструкции. | Возможный способ подключить `@docs/conventions.md`; его наличие в каждом проекте не предполагается. |
| Auto memory | Клиент выбирает `MEMORY.md` репозитория; агент читает и пополняет отдельные заметки. | `kb/projects/-home-stsiapan-main-claudefiles/memory/`. |
| Скилл `SKILL.md` | Инструкция для выбранной работы; полное тело читается при использовании. | `context7-mcp`, `dotnet-router`, `tldraw-offline`. |
| Хук | Программа запускается при событии и может вернуть текст агенту. | `SessionStart → detect-dotnet.sh → подсказка про dotnet-router`. Звуковой хук `paplay` просто играет звук. |
| Плагин | Доставляет скиллы, хуки и определения агентов. Его компоненты добавляют контекст своим способом. | В super включены superpowers, dotnet, codex. |
| MCP | Подключает инструменты. Их вызов приносит конкретные данные; сервер может давать и инструкции. | Запрос документации через Context7. Подключение сервера не означает, что вся документация уже прочитана. |
| Read, поиск, терминал, API | Результат вызова становится доступен в текущем разговоре. | Чтение `lib/kb.sh`; получение схемы через API TLDraw. |
| Подагент | Получает задание и переданный ему контекст; возвращает результат. Передача всей истории зависит от способа запуска. | Свежая подзадача и агент с унаследованным разговором получают разный исходный контекст. |
| Resume и compact | Resume продолжает сохранённый разговор; compact оставляет сводку вместо части длинной истории. | История разговора отдельна от заметок в KB; у профилей собственные каталоги истории. |
| Файл передачи работы | Сохраняет решения и остаток задачи. Следующая сессия открывает его. | `docs/vision/`, спецификация, план, handoff-файл. |
| Дополнительный системный промпт и настройки организации | Клиент может подключать текст через CLI или управляемые настройки. | Это возможности клиента; собственные обёртки `claude-super` и `claude-g` задают каталог профиля, без дополнительного `--system-prompt`. |

Описанная проводка KB настроена для **Claude Code**. Текущая сессия **Codex** может исследовать эти же файлы инструментами, но из этого не следует, что Claude-профили и их память автоматически подставлены в Codex. Для Codex существуют отдельные инструкции и настройки.

## Как проверить подключение самому

Эти команды выполняются **в том контейнере, где запускаешь Claude**. Поэтому `~` будет домашней папкой именно этого контейнера.

Посмотреть, куда ведёт общий индекс профиля super:

```bash
readlink ~/.claude-super/rules/kb-index.md
```

Посмотреть выбор рабочей области:

```bash
readlink ~/main/.claude/rules/context-index.md
```

У `personal` второй результат заканчивается на `/contexts/personal/INDEX.md`, у `stellium` — на `/contexts/stellium/INDEX.md`. На хосте при `kb.context=none` этой ссылки нет.

Прочитать именно текст индекса, который открывается через профильную ссылку:

```bash
cat ~/.claude-super/rules/kb-index.md
```

В самой сессии Claude команда `/context` показывает загруженные файлы инструкций, а `/memory` позволяет посмотреть места памяти и настройки auto memory. Это помогает различать «ссылка настроена на диске» и «файл действительно загрузился в конкретный запуск». Названия и подробности интерфейса зависят от версии Claude Code. [Документация команд памяти](https://code.claude.com/docs/en/memory#view-and-edit-with-memory).

## Где реализована эта настройка

- [`lib/profiles.sh`](../../lib/profiles.sh) выбирает каталоги профилей, устанавливает их компоненты и создаёт обёртки запуска.
- [`lib/kb.sh`](../../lib/kb.sh) создаёт правило KB и ссылки на общий, контекстный и машинный индексы.
- [`lib/py/kb_settings.py`](../../lib/py/kb_settings.py) записывает путь auto memory и разрешения чтения и редактирования базы.
- [`setup.sh`](../../setup.sh) вызывает настройку профилей и затем настройку рабочих папок.
- В соседнем репозитории dotfiles настроены домашние каталоги Distrobox и синхронизация KB. Distrobox даёт контейнерам отдельные домашние папки; Syncthing переносит файлы между устройствами.
