# Правила понятных диаграмм

Диаграмма должна объяснять устройство системы без дополнительной расшифровки в чате. Читатель должен узнавать, что это за объект, где он находится, что содержит и как связан с соседями. Эти правила собраны по пользовательским ревью и с 11 октября 2026 встроены в установленный скилл `tldraw-offline`.

## Как правила получает агент

При выборе скилла `tldraw-offline` агент читает его инструкции: раздел `Explain the system visually` содержит требования к объяснению, раздел `Operate the canvas` — работу с приложением и оформление. Напоминать про этот документ для работы в TLDraw не требуется. Автоматический выбор скилла зависит от совпадения запроса с его описанием; наличие скилла не означает, что его полный текст загружается в каждую сессию.

Исходник скилла хранится в репозитории `dotfiles`: `home/dot_local/share/tldraw-agent/tldraw-offline/SKILL.md`. Chezmoi устанавливает его в каждое окружение, а папки скиллов Claude и Codex подключают установленную версию. Если приложение установило собственную копию скилла, она сохраняет инструкции API и через `DOTFILES_STYLE.md` подключает наши правила. От расположения рабочего проекта это не зависит.

На этой машине обновлены хост и контейнеры `personal`, `digi3`, `stellium`. На других устройствах нужно получить обновлённый исходник `dotfiles` и выполнить `chezmoi apply` в нужных окружениях. Это доставка настроек через dotfiles, а не синхронизация памяти KB. При следующих ревью обновляйте и этот документ для человека, и раздел с правилами в исходнике скилла. Для диаграмм в других инструментах отдельное автоматическое подключение этих правил пока не настроено.

## Согласованные правила

1. **Один объект — один блок.** Разные файлы показываются отдельно: `CLAUDE.md` и `kb.md` нельзя объединять в один прямоугольник. У каждого файла своё назначение.
2. **Вложенность — деревом.** Профиль → папка `rules` → файл `kb-index.md` — три уровня и три объекта. Полный путь не заменяет дерево. Его можно дать мелкой технической подписью, если он нужен для поиска на диске.
3. **Сначала смысл, затем имя.** Основная подпись объясняет назначение; настоящее имя остаётся рядом. Например: «Оглавление общих заметок», ниже `kb-index.md`, отдельно пометка «симлинк».
4. **У файлов есть короткие примеры содержимого.** Для индекса достаточно двух характерных записей; для инструкции — небольшого фрагмента. Огромный текст сокращается, сохраняя представление о том, что хранится в файле. Перевод или пересказ помечается; его нельзя выдавать за дословную цитату.
5. **Категории раскрываются конкретикой.** У скиллов показываются реально установленные примеры и назначение каждого. Для неочевидного технического поведения прикладывается фрагмент кода или скриншот с пояснением, что он доказывает.
6. **Разные связи различимы.** «Лежит внутри», «симлинк на», «загружается при старте», «читается отдельным вызовом» и «переносится синхронизацией» нельзя обозначать одинаковыми безымянными стрелками. На канвасе есть короткая легенда.
7. **Одинаковые сущности оформляются одинаково.** Папки, файлы, ссылки и примеры имеют последовательное оформление и сопоставимую подробность. Нельзя произвольно объединять одни файлы и дробить соседние.
8. **Всё объяснение — на одном канвасе.** Используется одна страница TLDraw с понятным порядком чтения. Текстовые пояснения стоят рядом с соответствующими схемами, а объёмная справка может храниться отдельным документом.

## Пример применения

```text
Выбранный профиль
.claude-super
└─ Правила
   rules/
   ├─ Как пользоваться базой знаний
   │  kb.md — обычный файл
   └─ Оглавление общих заметок
      kb-index.md — симлинк
                  └─ ссылается на → База знаний → global → INDEX.md
```

Рядом с `INDEX.md` показываются, например, две реальные записи с короткими описаниями: `feedback-annotate-jargon` — пояснять технические термины; `branch-naming-convention` — соглашение о названиях Git-веток. Это примеры записей, а полные заметки хранятся отдельными файлами.

## Рабочие решения для следующего ревью

- Дерево описывает реальное расположение файлов. Перенаправленная память не изображается физически находящейся в профиле: настройка профиля связывается с папкой в KB.
- Симлинк и ссылка внутри текста различаются. Симлинк открывает другой файл через файловую систему; Markdown-ссылка только указывает, что агент может прочитать дальше.
- Текущее устройство и предложенные изменения явно разделяются. Схема памяти по постоянному идентификатору репозитория остаётся предложением, пока её не реализовали.
- Пользовательские наброски сохраняются перед полной перерисовкой. Результат проверяется по живому канвасу, крупным фрагментам и отсутствию наложений; затем обновляются сохранённый TLDraw и превью в репозитории.

## Проверка перед показом

Для каждого блока можно ответить: что это, где находится, что содержит и зачем связано с соседями. Примеры взяты из текущей настройки, а длинные пути и большие цитаты не мешают читать основную структуру. Визуальная проверка не заменяет следующий пользовательский раунд ревью.
