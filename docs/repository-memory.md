# Память по репозиторию

При настройке через Claude Files с включённой KB **любой Git-репозиторий получает память автоматически**. Регистрировать каждый проект не нужно. Профиль определяет поведение агента, адрес репозитория — его память, `kb.context` — дополнительное оглавление рабочей области.

## Пример без предварительной настройки проекта

```text
Ноутбук:     клон Widget в папке main
             origin = git@github.com:example/widget.git
                                ↓
                    github.com/example/widget
                                ↓
                 KB → repositories → widget-<хеш>
                                     ├─ MEMORY.md — память, загружаемая при старте
                                     └─ заметки, читаемые по необходимости
                                ↑
Рабочая машина: клон Widget в папке sources
                origin = https://github.com/example/widget
```

Хеш вычисляется из полного нормализованного адреса, включая сервер и владельца. Поэтому одинаковое имя у чужого форка не смешивает память. Путь клона, имя устройства, профиль и рабочая область в расчёт не входят. Корень KB может быть разным на устройствах; относительная папка проекта будет одинаковой. Для общих **заметок**, а не только одинакового выбора папки, устройства должны синхронизировать одну KB, как и раньше.

SSH/HTTPS, переименование папки, новый клон, вложенный каталог и worktree сохраняют память. Смена сервера или владельца меняет идентичность; для такого переезда есть aliases ниже.

## Что делает запускатель

1. `claude`, `claude-vanilla`, `claude-super` и `claude-g` вызывают общий запускатель `repo_memory.py launch`.
2. Он читает `flags.kb` и `kb.vault_path` этого окружения. При выключенной KB запускает настоящий Claude с исходными аргументами.
3. Git сообщает `origin`. Если его нет, берётся первый remote из `git remote`. Адрес нормализуется без пароля, имени пользователя и query-параметров.
4. Если есть явная привязка в `repositories.json`, выбирается её папка. Иначе автоматически вычисляется `repositories/<имя>-<24 hex символа SHA-256>/`. Общий реестр при этом не создаётся и не меняется.
5. Папка передаётся через `--settings` → `autoMemoryDirectory` только этой сессии. Общий `settings.json` профиля не переписывается.
6. Если `cwd` не в Git, дом выбирается по месту: `~/main` получает `contexts/<kb.context>/`, папка под ней получает `contexts/<kb.context>/projects/<имя первой папки>/`, всё остальное получает `machine/<kb.machine>/` на хосте или `contexts/<kb.context>/` в контейнере.
7. Оглавления контекста, машины и проекта передаются как справочные данные через `--append-system-prompt`; оглавление, совпадающее с `MEMORY.md` дома, второй раз не подаётся. Явная запись реестра может переопределить область.

Например, Widget из Personal и Digi3 использует одну проектную память, но оглавления областей разные. Глобальное оглавление продолжает подключаться правилом профиля. Остальные заметки читаются по необходимости.

Зонтичные симлинки под `~/main` и `~/system` больше не используются: `setup.sh` их снимает, оглавления подаёт запускатель.

## Установка на любой новой машине

Выполнить обычный `./setup.sh`, включить KB и указать её корень. В контейнере путь к общей KB обязателен. Для каждой следующей машины нужны те же действия и синхронизация KB; список проектов вводить не нужно.

Установщик сам ставит запускатель в `~/.local/share/claudefiles-runtime/`, команды профилей и `claudefiles-kb` — в `~/.local/bin/`. Он добавляет помеченный блок PATH в `.bashrc` и `.profile`, а также в существующие `.bash_profile`, `.bash_login`, `.zshrc`, `.zprofile`; для текущего zsh создаёт `.zshrc`, если его ещё нет. Пользовательский текст сохраняется, повторная установка блок не дублирует. Отдельная установка dotfiles для этого не требуется. Установки Claude от npm/native и их обновления сохраняются.

После установки открыть новый терминал. В уже открытом можно пользоваться `claude-vanilla`, `claude-super` или `claude-g` по их полному пути, либо перечитать настройки оболочки. Неинтерактивный процесс, который не читает shell rc, должен вызывать установленную профильную команду или shim явно.

Обновление исходников на другой машине само по себе не меняет установленную копию: после получения новой версии нужно повторить `setup.sh`. Подключение shell PATH поддерживает Bash/POSIX login profile и zsh; другим оболочкам нужен соответствующий PATH или явная команда профиля.

## Репозиторий без сетевого адреса

Для Git-репозитория без remote или с локальным файловым remote запускатель создаёт случайный постоянный ID в общей Git-папке: файл `claudefiles-memory-id`. Память хранится в `repositories/local-<хеш>/`. Перенос папки и worktree сохраняют ID. Рабочие и отслеживаемые Git файлы не меняются.

После добавления сетевого `origin` выбирается его общая папка; при её первой инициализации прежние локальные заметки копируются туда. Исходники сохраняются.

Два независимо созданных локальных репозитория нельзя автоматически признать одним проектом. Для совместного использования между машинами им нужен общий сетевой remote либо явная привязка. Копирование всей Git-папки сохраняет локальный ID, обычный `git clone` его не переносит. Каталог вне Git получает дом по месту (см. выше); прежний механизм по пути остаётся только для запуска в обход запускателя.

## Старые заметки

При первом запуске из существующего checkout запускатель ищет его прежнюю память в `projects/<старый slug>/memory/`. Если новая папка ещё не имеет `MEMORY.md`, заметки копируются, оглавление сохраняется, `INDEX.md` становится ссылкой на `MEMORY.md`. Это выполняется под локальной блокировкой. Старые файлы не удаляются. После инициализации старый источник больше не импортируется автоматически, чтобы не возвращать устаревшие факты поверх новой работы.

Если checkout **уже переехал**, по новому пути нельзя достоверно найти его старую память. Её можно импортировать явно, указав текущий репозиторий — регистрация для этого тоже не нужна:

```bash
# План без изменений:
claudefiles-kb migrate --vault ~/Documents/Notes/kb \
  --cwd /текущий/клон --source '<KB>/projects/<старое-имя>/memory'
# Применение:
claudefiles-kb migrate --vault ~/Documents/Notes/kb \
  --cwd /текущий/клон --source '<KB>/projects/<старое-имя>/memory' --apply
```

Конфликтующие одноимённые заметки останавливают импорт до копирования. Ограничение оглавления: 200 строк / 25 КБ. Прежние индексы назначения сохраняются в `.migration-backups/<id>/`. Источники остаются на месте. Тематические разделы `contexts/.../projects/...` не объединяются по совпадению имени: для привязки к такой библиотеке служит реестр.

## Необязательный реестр: переезды и существующие библиотеки

`<KB>/repositories.json` нужен для исключений: соединить старый и новый remote после переезда либо выбрать уже существующую тематическую папку.

```json
{
  "version": 1,
  "projects": [{
    "id": "example-widget",
    "remotes": ["github.com/example/widget", "git.example.com/team/widget"],
    "context": "personal",
    "memory": "repositories/widget-<хеш из resolve>"
  }]
}
```

`memory` здесь нужно взять из результата `resolve`, а не использовать текст-заполнитель. Для существующей библиотеки допустим также путь `contexts/<область>/projects/<проект>`. Все пути относительны к KB; `..`, абсолютные пути и выход через симлинки отвергаются. Дубли адресов и папок запрещены. `context: "none"` отключает оглавление области для этой привязки.

```bash
claudefiles-kb resolve --vault ~/Documents/Notes/kb --cwd /любой/клон

# Один и тот же id + папка + область: последующие register добавляют aliases.
claudefiles-kb register --vault ~/Documents/Notes/kb \
  --id example-widget --context personal \
  --remote 'git@github.com:example/widget.git' \
  --memory 'repositories/ПАПКА-ИЗ-RESOLVE'
```

Существующая явная привязка 1ANV сохранена. Для намеренного объединения форка или локального репозитория можно установить `git config claudefiles.memoryProject <зарегистрированный-id>`. Это дополнительная возможность, не обязательный шаг настройки проекта.

Реестр синхронизируется вместе с KB. Локальная блокировка защищает `register` на одной машине; одновременные изменения реестра на разных устройствах требуют разбора sync-conflict. Обычный автоматический выбор памяти реестр не пишет.

## Нормализация и границы

GitHub: хост, owner и repo приводятся к нижнему регистру. Остальные серверы сохраняют регистр пути. Azure поддерживает SSH `ssh.dev.azure.com:v3/...`, HTTPS `dev.azure.com/.../_git/...` и `<org>.visualstudio.com/.../_git/...`; все формы дают `azure:org/project/repo`. `.git` и стандартные порты не влияют на идентичность; нестандартные порты сохраняются. Подмодуль считается отдельным репозиторием.

Команды `mcp`, `plugin`, `auth`, `doctor`, установка/обновление и справка проходят напрямую. Аргументы сессии сохраняются, `--settings` объединяются; явный `autoMemoryDirectory` имеет приоритет. Дополнения системного промпта сохраняются. Ошибочная конфигурация останавливает запуск с сообщением вместо незаметного открытия другой памяти.

Абсолютный путь до установленного клиента или KB остаётся настройкой устройства; идентичность проекта от него не зависит. История чатов — отдельный механизм. Прямой вызов upstream-бинарника, в том числе из IDE, обходит запускатель: интеграции должны вызывать профильную команду или shim. Для Codex адаптер этой памяти пока не реализован; `autoMemoryDirectory` относится к Claude Code.

## Проверка

`bash skills/tools/test-repo-memory.sh` проверяет реальные локальные Git-репозитории и два чистых HOME: автоматический выбор без регистрации, разные устройства/контексты/пути KB, SSH/HTTPS, разные владельцы, worktree, локальные ID, добавление origin, импорт прежних заметок, конфликты, аргументы клиента и установку обычной команды через shell rc.

`test-setup-idempotent.sh` дополнительно проверяет полный `setup.sh` без dotfiles и без реестра: команда `claude` подключена, новый произвольный проект разрешается автоматически, повторная установка не меняет rc-файлы. `test-kb.sh` и `test-profiles.sh` проверяют существующую проводку и профили.

Используемые интерфейсы: [autoMemoryDirectory](https://code.claude.com/docs/en/memory#storage-location), [настройки и дополнение промпта при запуске](https://code.claude.com/docs/en/cli-reference#cli-flags).
